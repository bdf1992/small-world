# M0.7-C — Pack Requirement Circuit

Status: **alpha / stacked on M0.7-B**

This slice turns Pack slots from weighted fixture lists into typed authoring ports that can admit Cards through generic Requirements.

## Quality lines

> A Slot is a plain authoring handle for a compositional role plus a Requirement.

> Compatibility is determined by the Requirement contract, not by a special case for a named Card.

> Connecting a Card is not complete until the existing bounded resolver can place that Card into the committed World.

> The Scenario graph must follow the resolved World. It may not retain a stale authored fixture binding after a different candidate wins.

## Pack port contract

The Spire currently exposes two slots:

```text
Spire
├ guardian
│   └ Requirement: Artifact/Persona × 1
└ treasure
    └ Requirement: Artifact/Item × 1
```

The editor projects each slot as:

```text
Slot
├ role
├ Requirement
│   ├ accepts
│   └ count
├ connected candidates
└ compatible authored Cards
```

`Requirement` remains generic. There is no `ContextRequirement` or Ice-Dragon-specific Pack behavior.

## Card → Pack connection

The application authoring session now supports:

- `connectCard(slot, cardId, weight)`;
- `disconnectCard(slot, cardId)`;
- `setPackCandidateWeight(slot, cardId, weight)`;
- `focusPackCandidate(slot, cardId)` as an authoring convenience that leaves one candidate with support;
- compatibility inspection through `slot.requirement.accepts`.

A Card may connect only when its grammar satisfies the slot's accepted grammar.

Examples:

```text
Ice Dragon  Artifact/Persona  → Guardian  PASS
Frozen Crown Artifact/Item    → Guardian  REJECT
Frozen Crown Artifact/Item    → Treasure  PASS
```

## Authored Card runtime

M0.6 retained a specialized Dragon runtime for canonical parity. M0.7-C adds an optional authored-Card runtime registry to the horizontal world compiler.

This means:

```text
Pack chooses persona.ice-dragon
             ↓
template registry finds authored Template
             ↓
authored Card runtime contextualizes all its priors
             ↓
Virtual
             ↓
Instance
```

The world engine does not contain an `ice-dragon` branch.

Canonical `persona.dragon` still uses its specialized M0.6 implementation so prior accepted behavior remains stable while the generic authoring path is proven beside it.

## Canonical proof

```text
clone Dragon
    ↓
Ice Dragon Card
    ↓
Guardian Requirement accepts Artifact/Persona
    ↓
connect
    ↓
focus Ice Dragon candidate
    ↓
existing bounded DAG resolves Spire
    ↓
Mountains / Spire / guardian = Ice Dragon Instance
```

The committed Ice Dragon must retain authored Dragon possibility dimensions such as age and temperament as well as contextual element and rarity.

## Scenario graph correction

M0.7-A's canonical Scenario graph explicitly bound the Guardian slot to Dragon. That was valid only while Dragon was the fixed proof fixture.

M0.7-C replaces that assumption on the live authoring path. The Scenario graph now derives bindings from the actual committed Pack members:

```text
Spire.guardian ─bound-to→ <resolved guardian Template>
Spire.treasure ─bound-to→ <resolved treasure Template>
```

Contextual Signals and Influences are then projected against the contextual possibility nodes of whichever Cards actually occupy those slots.

So Card / Pack / Graph / Resolution / World remain different projections of the same current state rather than diverging stories.

## Browser surface

Pack mode now includes a lightweight circuit editor:

```text
Spire
│
├ Guardian port
│   Requirement Artifact/Persona
│   connected candidates + weights
│   compatible authored Cards → Connect
│   Focus → recompile → World
│
└ Treasure port
    Requirement Artifact/Item
    connected candidates + weights
    compatible authored Cards → Connect
```

The current committed Mountains Spire members are displayed on the same Pack surface so the author can see whether a connection changed the realized result.

This is functional alpha UI. Full visual consolidation remains M0.7-G.

## Acceptance

`npm run verify:packs` must prove:

1. Guardian exposes `Requirement.accepts = Artifact/Persona`;
2. Ice Dragon is discovered as compatible from the authored Card library;
3. connecting Ice Dragon adds a real Pack candidate tuple;
4. focusing Ice Dragon causes the actual Mountains/Spire guardian to become Ice Dragon;
5. the realized Ice Dragon retains authored age/temperament and contextual possibility evidence;
6. Frozen Crown is rejected from Guardian and admitted to Treasure;
7. disconnecting a Card removes the Pack candidate without leaving an invalid zero-support slot;
8. Scenario graph bindings follow actual resolved members rather than fixed Dragon assumptions;
9. Pack circuit JavaScript parses and its HTTP actions operate through the application port;
10. all inherited M0.5/M0.6/M0.7-A/B gates remain green.
