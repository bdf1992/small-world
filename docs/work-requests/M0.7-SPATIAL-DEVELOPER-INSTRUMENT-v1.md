## Objective

Build the smallest developer-facing instrument that can exercise and explain the clarified M0.7 model while preserving the useful whole-shape capability of frozen M0.5.

This is a **development tool**, not the game. It must not become a generic dashboard, fake game HUD, semantic fixture browser, or second simulation runtime.

The modeled objects should be the primary development handles:

```text
Map        → POI / topology / Relation / Traversal
Clock      → Face / Hand / Tick / rotation / Crossing
Hourglass  → bound Artifact / Grain / Neck / Crossing
Artifact   → Elemental Identity / Profile / Attributes / Properties / Statline / State
```

## Model lines the tool must preserve

1. Exactly eight Elements share one canonical cyclic ring:

   ```text
   Void → Fire → Chaos → Ground → Aether → Water → Order → Sky → Void
   ```

2. One canonical **Relation Wheel** defines `Is / Affinity / Anchor / Vice / Nemesis / Conflict / Need / Wants` by relative offset.
3. **Elemental Identity** is a weighted composition of one or more Elements. It is not Artifact instance identity and it is not a single winning Element.
4. Each participating Element rotates the same Relation Wheel to its own origin and contributes that reading at its Element weight.
5. The default Profile is the weighted overlay of all of those rotated contributions. Do not author one profile table per Element and do not discard minority contributions.
6. Attributes expose weighted elemental relations/deltas from the Profile for interaction.
7. Properties vary how an Artifact participates in resolution and may locally deform/interpret the default Profile without mutating the canonical Relation Wheel.
8. Stats are measurements. Rules may read them; measurements are not mutation authority by themselves.
9. State is the measured record of what is true at `T`, including the effective result of admitted local variations.
10. Traversal is actual movement through admitted topology.
11. Crossing requires witnessed passage through a meaningful boundary into a newly addressable State/Position.
12. Derived connection depth is explicit:

    ```text
    Virtual<Relation> → admitted/weighted Relation → optional Artifact.Road
    ```

13. Sprite output is generative presentation downstream from authoritative State.
14. Budget limits resolution depth without invalidating unresolved frontier.

## Whole-shape surface

Do not start from a blank dashboard. Preserve M0.5's useful world/clock/hourglass/instrument reachability while folding thick permanent chrome into progressive disclosure.

The interaction hierarchy is:

```text
┌─────────────────────────────────────────────────────┐
│ Map / topology field                                │
│                                                     │
│ POIs · boundaries · zones · Relations               │
│ selected Artifact · Position · Traversal            │
│ next Crossing · unresolved frontier                 │
├───────────────────────────┬─────────────────────────┤
│ Clock / Face              │ Hourglass / Artifact    │
│ Hand · Tick · current     │ Grain · Neck · bound    │
│ elemental seat/role       │ Artifact · crossing     │
└───────────────────────────┴─────────────────────────┘
```

This is not a prescribed pixel layout.

## Progressive disclosure

Use one spatial scene. Reveal evidence around the selected modeled object rather than replacing the scene with an unrelated inspector dashboard.

```text
Ambient → Select → Focus → Inspect
```

**Ambient** shows enough to understand topology, Clock position, Hourglass activity, active selection, and current movement/resolution pressure.

**Select** reveals immediate model facts about a POI, Artifact, Clock component, Hourglass, Relation, Traversal, or Crossing.

**Focus** exposes the selected object's directly relevant structure:

```text
Elemental Identity / weights
Profile contribution overlay
Attributes
Properties
Statline
State
Relations
Position
Virtual frontier / budget
```

**Inspect** exposes provenance:

```text
which Elements contribute to this Profile and at what weight?
how was each Relation Wheel rotated?
which Property/rule changed the effective reading?
which measured condition was read?
which Relation admitted this Traversal?
which boundary produced this Crossing?
what changed from State(T) to State(T+1)?
what remained Virtual and why?
which budget stopped deeper collapse?
```

## Required vertical proofs

The first implementation should be small, but it must prove the system rather than a hard-coded fixture.

### 1. Canonical wheel + weighted overlay

First prove the Relation Wheel is one deterministic rotation function for all eight origins.

For `Fire` as one contribution:

```text
Fire   = Is
Chaos  = Affinity
Ground = Anchor
Aether = Vice
Water  = Nemesis
Order  = Conflict
Sky    = Need
Void   = Wants
```

Then prove multi-Element Elemental Identity using at least:

```text
Fire  = 10
Water = 1
```

The developer instrument must expose both weighted contributions rather than selecting Fire and discarding Water:

```text
Fire wheel  × 10
+
Water wheel × 1
=
default Profile
```

The resulting contribution view should preserve the overlay shape:

```text
Fire    = Is×10       + Nemesis×1
Chaos   = Affinity×10 + Conflict×1
Ground  = Anchor×10   + Need×1
Aether  = Vice×10     + Wants×1
Water   = Nemesis×10  + Is×1
Order   = Conflict×10 + Affinity×1
Sky     = Need×10     + Anchor×1
Void    = Wants×10    + Vice×1
```

Do not require normalization merely to represent the overlay. A consuming rule may normalize or project the contributions later if its contract requires that.

A Property/rule must then be able to visibly vary the effective reading of this default Profile while leaving the canonical Relation Wheel and base Element weights inspectable.

### 2. State and measurement

Expose a real measured record:

```text
State(T)
  ├ Elemental Identity / weights
  ├ default Profile contribution overlay
  ├ effective Profile / Attributes
  ├ active Properties
  ├ Statline
  ├ Relations / Position
  └ Clock / Hourglass condition
```

If a Statline or State condition activates a Property or changes an Attribute/profile reading, the evidence chain must show that an admitted rule read the measurement, proposed the effect, and resolution settled it into the next State. Do not describe State or the measurement itself as mutation authority.

The instrument should make this distinction visible:

```text
Relation Wheel      = universal
Elemental Identity  = weighted default composition
Profile             = default overlay
rule / Property     = local interpretation / deformation
State               = measured result at T
```

### 3. Traversal and Crossing

At least one interaction must expose:

```text
State(T)
  ↓
entity at Address A
  ↓ Traversal through admitted topology
meaningful boundary
  ↓ CROSSING
entity becomes addressable at B
  ↓ rules / Properties / Relations / constraints / propagation
State(T+1)
```

The developer must be able to inspect the before State, path, boundary, conditions read, effects proposed, constraints/budget, after State, and unresolved frontier.

Clock Hand → Tick and Grain → Hourglass Neck are preferred proofs because they already exist in the model.

### 4. Relation depth

Make these visibly distinct:

```text
A ··· B
Virtual<Relation>
```

```text
A ─── B
admitted/weighted Relation
```

```text
A ─ Road.17 ─ B
materialized Artifact.Road
```

The resolver may stop at any level according to budget/constraints. The interface must not imply that only `Artifact.Road` is valid.

### 5. Generative Sprite projection

Expose presentation as a projection:

```text
authoritative Artifact State
        ↓
projection inputs / decision
        ↓
Sprite
```

Projection may use Artifact type, weighted Elemental Identity, Profile/Attributes, resolved Tokens, Properties, State, and presentation context to:

- choose a base sprite;
- recolor/palette-shift according to elemental contributions;
- choose/replace parts;
- add/remove overlays;
- vary pose/orientation/state presentation.

A `Fire 10 / Water 1` Artifact should therefore be able to project a strongly Fire-biased visual with a weaker Water contribution without changing its authoritative Element weights merely to obtain that look.

Changing Sprite projection must not silently mutate authoritative State.

## Model-owned gestures

The first slice should support only gestures that correspond to real application/model operations:

- select an Artifact/POI/Relation/Clock/Hourglass component;
- inspect Elemental Identity weights and each rotated Relation Wheel contribution;
- inspect the default Profile overlay and current effective Attributes;
- inspect Properties, Statline, State, budget, and Virtual frontier;
- step the Clock Hand through the Face to the next Tick;
- step/resolve Grain Traversal through an Hourglass Neck;
- inspect a derived `Virtual<Relation>`, admitted/weighted Relation, and materialized Road when present;
- follow one admitted Traversal and witness its Crossing;
- inspect Sprite projection separately from authoritative State.

Do not move simulation rules into browser handlers to make these gestures work.

## Architecture line

Preserve the M0.6 parity separation:

```text
capability / model
      ↓
application operation
      ↓
serializable projection
      ↓
interface gesture
      ↓
deterministic test
```

The browser is a development surface over the model, not the model.

## Do not build

- Card-per-Artifact-type symmetry such as `Card.Persona` / `Card.Item` / `Card.Biome`;
- speculative root fields such as body plan, mobility, cognition, age, elevation, relief, moisture, material, rarity, durability, attack speed, or travel speed;
- hard-coded Human/Elf/Dragon/etc. content presented as canon;
- separate elemental relation/profile tables per Element;
- a single-winner elemental resolver that erases valid secondary Element weights;
- generic dashboard panel sprawl;
- game-HUD chrome optimized for play;
- teleporting movement labeled as Crossing;
- mandatory Artifact materialization for every Relation;
- Sprite/presentation values promoted into simulation authority;
- a parallel runtime for the workbench.

## Smallest capable example

Prefer one composition that exercises existing structures rather than inventing content:

```text
Card.Artifact
  ↓ collapse
Artifact.Clock and/or Artifact.Hourglass
  ↓
Elemental Identity = Fire 10 / Water 1
  ↓
weighted Relation Wheel overlay → default Profile → Attributes
  ↓
one admitted Property/rule reading measured State or Statline
  ↓
local effective mapping differs while default remains inspectable
  ↓
real Traversal
  ↓
one witnessed Crossing
  ↓
State(T+1) + provenance
  ↓
generative Sprite projection biased by the weighted elemental composition
```

Map/POI relation depth may be demonstrated with a minimal derived connection fixture using existing topology rather than rich world content.

## Acceptance evidence

Machine evidence for the eventual implementation PR must prove:

1. The canonical Relation Wheel rotates deterministically for all eight Element origins.
2. A multi-Element Identity overlays two or more wheel readings deterministically while preserving each Element weight; `Fire 10 / Water 1` is the minimum proof.
3. Minority elemental contributions are not silently discarded by a dominant Element.
4. Artifact instance identity remains distinct/deterministic and does not collide with Elemental Identity semantics.
5. Property/rule variation changes the effective reading without mutating the canonical Relation Wheel or erasing the default Element weights/Profile provenance.
6. Statline/State measurements can be read by rules that admit later changes.
7. State(T) and State(T+1) are inspectably distinct measured records.
8. Crossing cannot be recorded without admitted Traversal and a boundary event.
9. Low budget leaves valid Virtual Relation/Artifact frontier.
10. `Virtual<Relation>`, admitted/weighted Relation, and materialized Road are distinguishable compatible depths.
11. Sprite projection is generative, inspectable, elementally biasable, and non-authoritative.
12. UI gestures invoke application operations rather than owning simulation rules.
13. Frozen M0.5 whole-shape capability remains reachable through the new progressive-disclosure surface.

## Owner acceptance line

Passing tests or satisfying this work request does not constitute owner acceptance of M0.7.

No implementation PR produced from this request should be merged merely because CI is green. Owner acceptance remains an explicit gate.
