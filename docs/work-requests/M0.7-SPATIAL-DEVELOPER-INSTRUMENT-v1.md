# M0.7 Spatial Developer Instrument — Work Request v1

Status: proposed work request; implementation not authorized by this document alone.

Base semantic branch:

```text
m0.7/generative-card-pack-correction
8a64fb80f9e896535e6eb4050366cab0a0a59df5
```

This work request depends on `docs/M0.7-CORE-GLOSSARY.md` and the minimal generator/reset in `docs/M0.7-MINIMAL-ARTIFACT-GRAMMAR.md`.

## Objective

Build the smallest developer-facing instrument that lets us inspect and exercise the newly clarified model without turning Small World into either:

- a generic dashboard;
- a fake game UI;
- a semantic fixture browser;
- a second runtime beside the simulation model.

The surface should make the modeled objects themselves the primary development handles while preserving deterministic evidence and progressive disclosure.

## Product boundary

This is a **development tool**, not the game.

It should expose the real model through a spatial instrument:

```text
Map        → POI / topology / relation / traversal
Clock      → Face / Hand / Tick / rotation / crossing
Hourglass  → bound Artifact / Grain / Neck / crossing
Artifact   → Identity / Profile / Attributes / Properties / Statline / State
```

The goal is not to make these objects decorative. The goal is to let a developer manipulate and inspect the same structures the model uses.

## Canonical model constraints

The interface and application layer must respect these glossary decisions:

1. There are exactly eight Elements in the canonical ring:

   ```text
   Void → Fire → Chaos → Ground → Aether → Water → Order → Sky → Void
   ```

2. Identity orients one canonical elemental relation Profile; do not author independent eight-value profiles for each Element.
3. Attributes express weighted elemental character through that Profile.
4. Properties vary, constrain, gate, or interpret Attributes and other admitted relationships.
5. Stats/Statlines are measurements that may be both cause and consequence in bounded resolution.
6. State is the measured record at `T`, not the behavior that mutates the world.
7. Traversal is real movement through admitted Relations.
8. Crossing requires witnessed passage through a meaningful boundary into a newly addressable state.
9. Relations may remain derived/Virtual and may optionally resolve into Artifacts such as Roads when budget/detail requires it.
10. Sprite output is generative presentation downstream from authoritative state.

## Minimum whole-shape surface

Do not start from a blank dashboard. Preserve the whole-product utility of the frozen M0.5 workbench while replacing thick permanent chrome with model-owned controls and progressive disclosure.

The minimum visible composition should include:

```text
┌─────────────────────────────────────────────────────┐
│ Map / topology field                                │
│                                                     │
│   POIs, boundaries, zones, derived relations        │
│   selected Artifact / current Position              │
│   possible traversal / next Crossing                │
│                                                     │
├───────────────────────────┬─────────────────────────┤
│ Clock / Face              │ Hourglass / Artifact    │
│ hand + current seat       │ grains + neck + bound   │
│ CW / CCW relation         │ Artifact                │
└───────────────────────────┴─────────────────────────┘
```

This is an interaction hierarchy, not a prescribed pixel layout.

## Progressive disclosure

Use one spatial scene with evidence revealed around the selected modeled object.

Preferred disclosure ladder:

```text
Ambient → Select → Focus → Inspect
```

### Ambient

Show enough structure to understand world topology, Clock position, Hourglass activity, selected/active Artifact, and current movement/resolution pressure.

### Select

Selecting a POI, Artifact, Clock component, Hourglass, relation, or traversal should reveal only the immediate model facts needed to understand it.

### Focus

Focus should expose the object's directly relevant composition and next possibilities:

```text
Artifact
  Identity
  rotated Profile
  active Attributes
  active Properties
  Statline
  measured State
  admitted Relations
  current Position
```

### Inspect

Inspect reveals provenance/evidence without replacing the scene with a generic dashboard:

```text
why this Identity/Profile orientation?
which Property changed this Attribute?
which Statline condition became satisfied?
which relation admitted this traversal?
which boundary produced this Crossing?
what changed from State(T) to State(T+1)?
what remained Virtual and why?
which budget stopped deeper collapse?
```

## Required interactions

The first implementation slice should support a deliberately small set of gestures over real model operations.

### Artifact

- select an Artifact;
- inspect Identity and derived rotated Profile;
- inspect current Attributes, Properties, Statline, and State;
- inspect unresolved/Virtual frontier and collapse budget;
- inspect presentation Sprite separately from authoritative state.

### Clock

- manipulate or step the Hand through the Face rather than relying on disconnected toolbar buttons;
- expose current Element seat / relation role;
- show the traversal from one Tick/address to the next;
- record the Crossing and resulting State transition.

### Hourglass

- inspect the bound Artifact;
- show Grain positions and Neck boundary;
- step/resolve Grain traversal through the Neck;
- show which Attributes/Properties/State affected the crossing;
- show the resulting measured State.

### Map / POI

- select POIs and addressable topology;
- expose derived weighted Relations between relevant points;
- distinguish a derived Relation from a materialized `Artifact.Road`;
- show current Position and an admitted traversal path;
- witness a boundary Crossing rather than teleporting the entity to the destination.

## Relation materialization proof

The interface should make the following states visibly distinct:

```text
A     B
● ··· ●
Virtual / candidate relation
```

```text
A ─── B
admitted weighted relation
```

```text
A ─ Road.17 ─ B
materialized Artifact.Road
```

The resolver may stop at any of these levels according to budget and constraints. The UI must not imply that only the most materialized form is valid.

## Elemental profile proof

The instrument must prove that profiles are rotations of one canonical relation shape.

For example, selecting Identity `Fire` should derive:

```text
Fire   = Is
Chaos  = Affinity
Ground = Anchor
Aether = Vice
Water  = Nemesis
Order  = Conflict
Sky    = Need
Void   = Wants
```

Changing Identity should rotate those relative roles without loading or authoring a second profile table.

Properties may then visibly adjust weights/interpretation as deltas over that canonical orientation.

## State / crossing proof

At least one interaction must expose an explicit sequence:

```text
State(T)
  ↓
position at Address A
  ↓ traversal along admitted Relation
meaningful boundary
  ↓ CROSSING
position/address B becomes occupied
  ↓ rules / Properties / measurements / propagation
State(T+1)
```

The developer must be able to inspect:

- before state;
- path/traversal;
- exact boundary crossed;
- conditions read;
- effects proposed;
- constraints/budget applied;
- after state;
- unresolved frontier.

## Generative Sprite proof

The instrument should make Sprite projection visibly downstream from state.

A Sprite may be derived from some combination of:

```text
Artifact type
Identity / elemental orientation
resolved Tokens
Properties
State
presentation context
```

The projection may:

- choose a base sprite;
- recolor/palette-shift;
- choose or replace parts;
- add/remove overlays;
- vary pose/orientation/state presentation.

Changing the Sprite projection must not silently mutate authoritative Artifact State.

A developer should be able to compare:

```text
authoritative inputs
        ↓
projection decision
        ↓
rendered Sprite
```

## Architecture line

Use the same separation already established by M0.6 parity restoration:

```text
capability / model
      ↓
application operation
      ↓
serializable projection
      ↓
interface gesture
      ↓
deterministic test
```

Browser/UI code must not own simulation rules.

## What not to build

Do not introduce:

- `Card.Persona`, `Card.Item`, `Card.Biome`, or Card-per-type symmetry;
- body plan, mobility, cognition, age, elevation, relief, moisture, material, rarity, durability, attack speed, travel speed, or similar semantic root fields;
- hard-coded Human/Elf/Dragon/etc. content as if it were canonical;
- a second independent elemental profile table for each Identity;
- generic dashboard panel sprawl;
- a game HUD optimized for play rather than development;
- teleporting map movement disguised as Crossing;
- a requirement that every Relation materialize as an Artifact;
- presentation Sprite state as simulation authority.

## First vertical proof

The preferred first vertical slice is intentionally small:

```text
1 Card.Artifact
  ↓ collapse
1 Artifact.Clock or Artifact.Hourglass
  ↓ Identity orientation
canonical Profile
  ↓
Attributes + one Property + one Statline condition
  ↓
real Traversal
  ↓
1 witnessed Crossing
  ↓
State(T+1)
  ↓
generative Sprite projection
```

The selected example should use only semantics already admitted by the repository. Do not invent a rich creature/item ontology merely to demonstrate the mechanism.

## Acceptance evidence

Machine evidence for the implementation slice should eventually prove:

1. canonical Profile rotation is deterministic for all eight Identity seats;
2. Property variation changes effective readings without mutating the canonical ring/profile definition;
3. Statline conditions can participate in later resolution rather than being terminal-only values;
4. State(T) and State(T+1) are inspectably distinct measured records;
5. Crossing cannot occur without an admitted traversal path/boundary event;
6. low budget leaves a valid Relation/Artifact frontier rather than invalid state;
7. materialized Road and derived Relation are distinguishable but compatible representations;
8. Sprite projection changes are downstream and non-authoritative;
9. browser/UI gestures invoke application operations rather than implementing simulation rules;
10. frozen M0.5 whole-shape capability remains reachable rather than being deleted for visual cleanliness.

## Owner acceptance line

Passing tests or satisfying this work request does not constitute owner acceptance of M0.7.

No implementation PR produced from this request should be merged merely because CI is green. Owner acceptance remains an explicit gate.
