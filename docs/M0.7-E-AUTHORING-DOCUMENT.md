# M0.7-E — Plain-Data Authoring Document

Status: **machine-verified slice; owner acceptance pending**

This slice gives authored Small World content a portable, deterministic plain-data representation without serializing a solved world.

## Quality lines

> **Serialize meaning, not realization.**

> **A document may recreate the same authored graph; it must not smuggle a solved world into storage.**

The portable document is an authoring boundary, not a save-state format.

## Format

Authoring Document v1 is versioned JSON:

```json
{
  "format": "small-world.authoring",
  "version": 1,
  "cards": {},
  "packs": {}
}
```

The current slice supports:

- all authored Cards supported by M0.7-B;
- the current `pack.spire` composition from M0.7-C;
- Card fixed fields, priors, rules and slots;
- Pack candidate connections and weights.

## Deliberately excluded

The document does not contain:

- seed;
- resolution budget;
- authoring UI selection;
- resolution revision;
- solve trace;
- stop/frontier state;
- Reference objects;
- Virtual objects;
- Instance objects;
- committed World projection;
- simulation/clock/hourglass state.

Those are runtime, lifecycle, projection, or session concerns.

A runtime field added at the document root is rejected instead of ignored.

## Canonical Pack boundary in v1

M0.7-C currently allows editing Spire candidate connections and weights but does not yet allow arbitrary Pack CRUD, Slot creation, or Rule editing.

Therefore Authoring Document v1 serializes the complete Spire Pack shape for readability, but validates its currently non-editable fields against the canonical Pack definition:

- Pack id is canonical;
- Pack grammar is canonical;
- fixed fields are canonical;
- priors are canonical;
- rules are canonical;
- slot names are canonical;
- each slot's Requirement grammar and cardinality are canonical.

The mutable authored portion is the connected candidate set and its weights.

This avoids accepting document data that the current authoring session would silently ignore.

## Deterministic serialization

The document envelope, Card ids, Pack ids, and Card/Pack envelope fields use canonical ordering. Authored inner order inside fields such as priors, rules, slots, and candidate maps is preserved.

That distinction matters because authored projection order is part of the current editor/graph contract: loading the same authored document must not arbitrarily reorder possibility fields or candidate presentation simply because JSON was round-tripped.

The required invariant is:

```text
serialize
    ↓
parse + validate
    ↓
serialize
    =
identical bytes
```

The stronger E proof also requires Card and Pack tuple projections to retain their authored ordering across export/import.

The serialized text ends with one newline so it can later live cleanly in repository files.

Array order remains meaningful and is preserved.

## Whole-document validation

Import validates the complete document before any live authoring mutation occurs.

Validation includes:

- format/version;
- supported top-level fields;
- Card identifiers;
- Card grammar and required dimensions;
- weighted prior validity;
- contextual affinity validity;
- canonical Dragon retention while M0.6 parity remains under custody;
- supported Pack ids;
- canonical non-editable Spire fields;
- known Pack candidates;
- candidate grammar compatibility with the Slot Requirement;
- non-negative finite candidate weights;
- at least one supported candidate per Pack slot.

## Atomic import

A failed import must leave the current authored session unchanged.

No partial Card library replacement, Pack connection, or revision increment is allowed before validation succeeds.

One successful document import is one authoring revision.

It does not increment `resolutionRevision` because importing authoring truth is not a compute-budget operation.

## Round-trip proof

The canonical E proof is:

```text
Dragon Card
    ↓ clone/edit
Ice Dragon Card
    ↓ connect/focus
Spire Guardian
    ↓ export
Authoring Document v1
    ↓ stable JSON
fresh authoring session
    ↓ validate/import
same Cards + same Pack tuples
    ↓ full bounded resolve, same seed
Mountains / Spire / Guardian = Ice Dragon
```

The result demonstrates that the document recreates authoring truth and lets the existing compiler/resolver recreate realization; the realization itself was never serialized.

## HTTP application port

The workbench exposes:

- `GET /api/authoring/document` — structured Authoring Document JSON;
- `GET /api/authoring/document.txt` — deterministic serialized JSON text;
- `POST /api/authoring/document` — whole-document validate + atomic import.

The POST body is capped at 1 MiB for this slice.

The browser does not implement the schema or lifecycle rules.

## Browser surface

The Authoring & Resolution workbench contains a compact collapsed **Authoring Document** panel with:

- Export current;
- editable JSON text;
- Validate + import;
- format/version/Card/Pack summary;
- server validation feedback.

This is intentionally utilitarian. M0.7-G owns visual consolidation.

## Verification targets

`npm run verify:document` must prove:

1. authored Ice Dragon + Spire wiring exports;
2. runtime/lifecycle/session state is absent;
3. serialize → parse → serialize is byte-stable;
4. a fresh session imports the document as one authoring revision;
5. resolution revision remains unchanged;
6. imported Card and Pack tuple truth matches the source, including authored projection order;
7. same seed/full budget resolves the imported Ice Dragon through the existing world compiler;
8. wrong version is rejected atomically;
9. runtime-field smuggling is rejected atomically;
10. wrong-grammar Pack candidates are rejected atomically;
11. unknown candidates are rejected atomically;
12. unsupported Pack-rule mutation is rejected atomically;
13. all-zero candidate support is rejected atomically;
14. malformed JSON is rejected atomically;
15. HTTP export/import reproduces exact document bytes.

The full inherited test suite must remain green.

## Not repository persistence yet

This slice deliberately stops at a portable document and application transport.

It does **not** make the browser write repository files or choose source-control policy.

A later persistence layer can store this exact plain-data document rather than inventing another content model.

## Deliberately deferred

- arbitrary Pack create/delete/clone;
- arbitrary Slot creation;
- editable Pack Rules;
- schema migrations beyond v1;
- multi-document dependency/package resolution;
- repository path/naming policy;
- persistent runtime checkpoints;
- world landing/backward lineage UX (M0.7-F);
- shared visual language (M0.7-G).
