# M0.7-A — Typed Tuple Graph & Recompiling Authoring Foundation

Status: **alpha / stacked owner-QA work**

Base: `m0.6/parity-restoration`

This slice begins M0.7 by making the relationship between authored game content, the generative resolver, and the realized world directly inspectable and editable without giving the browser custody of world rules.

## Quality lines

> **Graph is truth; tree is viewpoint.**

> **Plain handles remain plain even when their substrate is generic.**

A Card, Pack, Region, Requirement, Rule, Signal, Influence, lifecycle graph, and World projection may all be represented over the same typed tuple substrate. That does **not** mean their user-facing meanings are flattened together.

- **Card** — object possibility authoring view.
- **Pack** — compositional possibility authoring view.
- **Region** — bounded spatial/context view.
- **Requirement** — a condition/binding that must be satisfied or supplied.
- **Rule** — graph conditions that derive or transform information.
- **Signal** — an addressable typed carrier of information/pressure.
- **Influence** — a derived contribution/effect relationship from a source or Signal to a target.
- **Virtual** — a valid graph whose unresolved bindings remain explicit possibilities.
- **Instance** — a stronger committed lifecycle projection.

There is deliberately no `ContextRequirement`. Context is one possible scope/source for an ordinary **Requirement**.

Signal and Influence are deliberately separate. A Signal may exist, route, decay, or target something without the word `Signal` also meaning its derived effect.

## Minimal tuple substrate

The structural primitive remains small:

```text
(subject, predicate, object)
```

A tuple may additionally carry identity and qualifiers when the relation itself needs to be inspected or attributed.

Predicates currently belong to semantic families:

```text
structural   is-a · has · contains · part-of · adjacent-to · bound-to
authoring    property · possibility · slot · candidate · default · rule
constraint   requires · accepts · count · bounds · excludes
dynamic      emits · targets · carries · influences · decays
derivation   derives · transforms · satisfies · resolves-to
evidence     derived-from · selected-because · blocked-by · supersedes
```

The family tells an interface or engine operation what kind of meaning an edge participates in. It does not require separate graph storage systems.

## Canonical proof slice

M0.7-A deliberately proves one narrow vertical crossing using existing content rather than introducing a large new schema.

```text
Dragon Card
    │
    ├── Requirement → Signal<ElementField>
    │                     ▲
    │                     │ emits
    │                 Mountains
    │
    └── possibility: element
             ▲
             │ influences
       Mountains ElementField Signal

Spire Pack
    │
    ├── guardian Requirement → Artifact/Persona
    │       ├── Dragon .66
    │       ├── Bandit .20
    │       └── Bear   .14
    │
    └── treasure Requirement → Artifact/Item
```

The existing immutable Dragon and Spire Templates are projected into tuples. The Mountains Region is projected as context and emits a typed `Signal<ElementField>`. A separate Influence links that Signal to the Dragon element possibility.

The existing bounded world resolver then supplies the actual lifecycle/result graph. M0.7 does not maintain a second fake resolution model.

## Recompiling editor contract

The authoring session currently supports a deliberately small set of draft mutations:

### Dragon Card

- rarity candidate weights;
- age candidate weights;
- temperament candidate weights;
- contextual element affinity: `weak | medium | strong`.

The contextual element distribution is **not** directly author-weighted in this slice. It remains a Requirement satisfied by the Region's typed ElementField Signal, then converted into a Virtual possibility distribution by the existing Dragon lifecycle logic.

### Spire Pack

- guardian candidate weights;
- treasure candidate weights.

Every edit performs this path:

```text
Card / Pack draft
      ↓
immutable draft Template
      ↓
existing horizontal-world compiler
      ↓
existing bounded DAG
      ↓
Reference → Virtual → Instance
      ↓
application World projection
      ↓
Card / Pack / Graph / Resolution / World views refresh
```

An editor mutation that only redraws the UI is not accepted.

## Current views

The Authoring & Resolution workbench exposes five projections over the same current draft/result:

```text
Card
  rooted authored tree

Pack
  rooted compositional tree

Graph
  shared typed tuple truth

Resolution
  lifecycle / realization traversal

World
  realized application projection
```

Card and Pack are rooted tree projections, not separate storage models.

## Solve Trace terminology

M0.6 called the DAG execution trace `signals`. That word is now reserved for typed addressable world/runtime Signals.

M0.7 introduces **Solve Trace** as the primary inspection term. A temporary `signals` compatibility alias remains for older M0.6 consumers and should be removed after dependent surfaces migrate.

## Executable acceptance

`npm run verify:graph` must prove at least:

1. generic Requirements are represented without `ContextRequirement`;
2. Signal and Influence are distinct graph semantics;
3. Dragon and Spire project from existing Templates into the tuple graph;
4. Mountains emits `Signal<ElementField>`;
5. the Signal targets and separately influences Dragon's element possibility;
6. Card and Pack tree views are rooted traversals over the graph;
7. the actual world resolver projects lifecycle `resolves-to` transitions;
8. editing Spire guardian weights can change the realized guardian for the same seed;
9. editing Dragon rarity can change the realized Dragon through the same resolver;
10. contextual affinity changes the Virtual element possibility distribution;
11. invalid/all-zero candidate groups are rejected;
12. the HTTP authoring adapter performs the same edits and rebuilds the realized World.

## Deliberate non-goals for this alpha

This is not yet a general content management system.

- Draft edits are in-memory session state; they do not write repository content.
- No arbitrary Card/Pack create/delete/clone contract exists yet.
- No general Requirement graph query engine has replaced existing authored candidate lists yet.
- Rules are projected but not visually/programmatically editable yet.
- Budget controls/frontier visualization are not yet part of this authoring editor.
- M0.5 spatial/time state and the M0.6 generative graph are not yet causally unified.
- This branch must not bypass the M0.6 parity-restoration owner gate.
