# M0.6 — Bounded Generative World

## Objective

Prove that a small recognizable game world can be authored through plain Definitions, Templates, and References; compiled into a bounded deterministic solve; inspected as Virtual possibility; and realized into replayable Artifact and Situation Instances.

M0.6 is not a full game-content milestone and not a production framework rewrite.

## Starting evidence

The Catalyst M0.5 vertical slice already demonstrates the difficult causal spine:

```text
clock tick
  → elemental-time supply
  → hourglass transfer
  → threshold / unmet demand
  → pressure
  → biome field
  → recursive field / spawning
```

It also demonstrates deterministic replay, Day/CW versus Night/CCW elemental interpretation, graph-local temporal pressure diffusion, biome/Persona/Event hourglasses, recursive child previews, and deterministic seed-addressed generation.

M0.6 preserves that evidence while moving content semantics above a smaller solver contract.

## Milestone question

> Can a bounded generative graph drive an actual tiny world while normal content authors work only with simple modeling handles?

## Scope

### Content set

Persona Cards:
- Bandit
- Bear
- Dragon

Biome Cards:
- Swamp
- Desert
- Mountains

Item Cards:
- Sword
- Staff
- Shield

Pack Templates:
- Cave
- Ruin
- Spire

Instruments:
- Clock
- Hourglass

### Canonical world envelope

Initial tests should target approximately:

- 3 Biome Instances
- 3–6 Situation Instances
- 8–20 ordinary Artifact Instances
- 1 global Clock
- an Hourglass for each eligible Artifact
- collapse depth of approximately 3–4 hops

The entire canonical world should remain small enough to inspect as one graph.

## Workstreams

### A — Freeze M0.5 evidence

- preserve the vertical slice as reference material;
- record source hashes and acceptance behavior;
- preserve canonical replay/digest evidence where practical;
- do not treat the single-file prototype as the new module architecture.

### B — Separate concerns

Extract explicit boundaries between:

- kernel/solver math;
- generative model;
- runtime state/commit;
- content;
- inspection/lineage;
- presentation.

This stage should intentionally avoid behavior changes.

### C — Formalize the model

Implement the lifecycle:

```text
Definition → Template → Reference → Virtual → Instance
```

and shared concepts:

```text
Card · Pack · Section · Slot · Region
Attribute · Property · Stat · Rule
```

### D — Bounded DAG solving

Introduce:

```text
SolveBudget {
  maxHops
  maxSlots
  maxInstances
}
```

A solve may stop with unresolved Virtuals. It may not exceed its budget by forcing realization.

### E — Horizontal content

Express the M0.6 content set without adding content-specific branches to the solver.

### F — Instruments

Represent Clock and Hourglass through the same model lifecycle so future Clock Faces, Hands, Hours, Hourglass parts, Locks, Filters, and related player-configurable content do not require parallel engines.

### G — Inspection

Support at least four inspection modes:

- **Facts** — committed world state;
- **Possibilities** — current Virtual candidates/ranges;
- **Lineage** — Definition/Template/Reference/Virtual path and causes;
- **Signals** — optional engineering-level solver trace.

### H — Certification

Add deterministic seed fixtures, replay checks, budget sweeps, invariants, and architecture notes.

## Non-goals

M0.6 does not require:

- multiplayer/networking;
- production persistence;
- polished final-game UI/art;
- hundreds of Templates;
- final-scale performance;
- a generalized plugin ecosystem;
- arbitrary user-authored scripting;
- proving every future Artifact family.

## Acceptance criteria

M0.6 is complete only when:

1. Content can be authored without understanding solver internals.
2. Solver code contains no Bandit/Bear/Dragon/Swamp/Sword/Cave/etc. special cases.
3. Cards and Packs compile through shared generative primitives.
4. Fully settled runtime Stats appear only on Instances.
5. Virtuals may legally remain unresolved.
6. Every solve obeys `maxHops`, `maxSlots`, and `maxInstances`.
7. Budget exhaustion cannot cause runaway recursive materialization.
8. Every Instance retains Definition → Template → Reference → Virtual lineage.
9. Same seed + same prior state + same actions + same budget yields the same result.
10. Changing a budget yields a deterministic different degree of resolution rather than an invalid world.
11. Clock and Hourglass use the same model system as other generative content.
12. World feedback occurs between deterministic solve/commit steps rather than uncontrolled cycles inside one solve.
13. A new Persona Template can be added without solver/runtime modification.
14. The canonical world can be inspected as one understandable graph.
15. M0.5 deterministic evidence remains available as a regression/reference baseline.

## Proposed delivery sequence

### M0.6.0 — Baseline preservation
Freeze/reference M0.5 evidence.

### M0.6.1 — Separation
Separate concerns with no intentional behavior change.

### M0.6.2 — Generative model
Introduce lifecycle and shared Section/Slot skeleton.

### M0.6.3 — Bounded solver
Introduce bounded DAG traversal, propagation, and collapse.

### M0.6.4 — Horizontal world
Generate the canonical small world from the scoped content set.

### M0.6.5 — Instruments
Move Clock and Hourglass through the shared model.

### M0.6.6 — Inspector
Expose Facts, Possibilities, Lineage, and Signals.

### M0.6.7 — Certification
Replay, seed, budget, and architecture validation.

## Estimate

Prototype engineering envelope: **35–60 focused engineering hours** assuming the existing M0.5 implementation is reused as evidence and behavior reference, and M0.6 does not simultaneously productionize the UI or persistence layer.

The bounded DAG solver and preservation of deterministic semantics are the highest-uncertainty workstreams.

## Governing heuristic

> The kernel may become more sophisticated only when the handles above it remain at least as simple.
